# 《切问近思》V0.3 实现方案

> 对照 `切问近思-作品文档-V0.3.md`。原则：不推倒重来，沿现有 B/S 骨架改心脏；冻结扩展；先打通「一问、一验、一礼」。  
> 未做实的能力一律走新接口，旧 `verify_scores` 数值徽章下线，不得继续当正式结果。

---

## 0. 现状与改造边界

| V0.3 要求 | 现有代码 | 差距 |
|-----------|----------|------|
| 论断绑定实际使用的证据 | `orchestrator` 生成一段话，`citations` 是全部 Top-k | 无 claim 结构，引用≠使用 |
| 经/注/用/译分轨 + 离散核验状态 | `_verify()` 写死 textual/modern/cultural 分数 | 必须整段替换 |
| 图谱进入问答证据链 | `graph_store` + `/graph` 页独立 | `run_chat` 未调用图 |
| 仪礼规则有出处/时代/抽象说明 | `liHostLogic` + `liHostData` 硬编码阈值 | 无 `source_ref`、无复盘回章句 |
| 600 题评测 + 基线消融 | `eval_rag.py` 约 10 条 | 协议在第 4 章，实现几乎空白 |
| 学习档案 / 复盘建议 | 君子之路成绩 | 无「已读出处、核验警示、演练错误」 |

**冻结（V0.3 §1.3.5 / 6.5.3）：** 乐射御书数新关卡、feed、共创、机构运营、第三种以后的语言。只修阻断故障。

**不改：** Docker 三件套、游客鉴权、`ref_id` 书篇句树、通义网关、礼艺 3D 场景几何（改规则数据，少改 Three 网格）。

## 1. 目标架构（对照 V0.3 §2.1–2.4）

把现在的「一段 stream + 三个分」改成三条链共用一份编排：

```text
POST /api/v1/chat
  → classify_query          # 单句 / 注疏 / 关系 / 比较 / 不可回答
  → retrieve_text           # 原文+注疏+译文，带 type
  → graph_evidence_path     # 仅关系/比较题
  → pack_evidence_bundle    # 分型、重排，记下 bundle_id
  → generate_claims         # JSON 论断，每条 track + evidence_refs
  → verify_claims           # 支持/部分/无依据/冲突/争议
  → intercept               # 无依据且语气确定 → 降级或拒答
  → SSE: claim / evidence / status / done
```

前端不再渲染 `verify.textual` 数字，改为论断卡 + 证据卡 + 离散状态（§3.1.3）。

仪礼链独立，演练结束用 `source_ref` 跳回阅读：

```text
GET  /practice/li/{scene}
POST /practice/li/{scene}/event     # 逐步事件，便于状态机回放
POST /practice/li/{scene}/result
GET  /practice/li/{scene}/recap     # 规则出处 + 相关 ref_id
```

## 2. 数据层（先改模型，再写算法）

对应 V0.3 §3.2。建议新增表，旧表增量字段，避免一次大迁移失败。

### 2.1 证据与论断

在 `models.py` 增加（名称可微调）：

```text
works              # 从 books 升一档：version, license, publisher
passage_spans      # passage_id, span_id, start, end, text   # 一句多命题
graph_edges        # + source_ref, source_excerpt, review_status
claims             # 见文档 3.2.2
claim_evidence     # claim_id, ref_id, span_id, used:bool
query_logs         # question, qtype, bundle_json, model, verifier_version
```

`messages` 增加 `claims_json`，保留旧 `citations` 一段时间只读兼容，**停止写入 `verify_scores` 作为对外结果**。

### 2.2 仪礼规则库

把 `liHostData` 里的阈值抽到数据，不要继续只写在 TS 里：

```text
li_rules           # 文档 3.2.3 全字段
li_rule_examples   # 正/过/不及/边界/冲突 各至少 1
li_events          # 一次演练的状态转移日志
```

前端 `liHostLogic.ts` 改为：本地先跑手感，**最终判定以服务端规则版本为准**（防改客户端作弊，也满足 §4.6.1）。

### 2.3 语料治理（§3.2.4）

第一期只锁《论语》一个版本 + 有限注疏（建议：朱熹《集注》选段或已有 `annotations`）+ 1 个英译本。产出 `docs/data-card-lunyu.md`：版本、许可、覆盖篇目、不支持的问题类型。

不做：继续 `expand_corpus` / 灌海外用户。那些与三项价值无关。

## 3. 三条链怎么落地

### 3.1 可溯源链 — 图文协同检索（核心创新二）

**新文件建议**

| 文件 | 职责 |
|------|------|
| `services/query_classify.py` | 规则优先：关键词/句式分 5 类；开发集后再上小模型 |
| `services/evidence_bundle.py` | 分型 Evidence（original/annotation/translation/graph）+ 重排 |
| `services/graph_evidence.py` | 调 `graph_store.path/neighborhood`，边必须带 `source_ref`，无来源的边不进问答 |
| 改 `retrieval.py` | `Evidence` 增加 `ev_type`, `span_id`, `source_meta` |

**实现顺序**

1. 扩展 `Evidence` 数据结构，关键词与向量两条后端都填 `ev_type`。  
2. `query_classify`：先规则（含「何谓/what is」→ 单句；「与…关系/versus」→ 关系；证据分低 → 不可回答）。  
3. 关系题：从问句抽概念 id（`concepts.zh` / 别名表），`path(a,b)` 取最短路，路上每条边必须有 `source_ref`，把对应 `passages` 并入束。  
4. 重排：第一期用可解释的线性分（相似 + 类型先验 + 图距离），权重只在**开发集**上调，测试集封存。公式进实验记录，不写死进创新表述。  
5. **关键约束：** 生成阶段只把束里的编号传给模型；核验阶段 `evidence_refs` 只能是束内 id，禁止把未使用的 Top-k 写进引用（§3.2.2）。

**验收：** 关系题 SSE 里出现 `graph_path` 事件；单句题不强制出图。消融「去图」后多跳 Recall 应下降，否则图不进创新点。

### 3.2 可核验链 — 分轨论断 + 支持判断（核心创新一）

**禁止：** 继续用 `_verify()` 三个 float。

**生成（两步，§3.3.2）**

1. 模型只输出 JSON（或 tool call），例如：

```json
{
  "claims": [
    {
      "claim_text": "...",
      "track": "jing|zhu|yong|yi",
      "evidence_ids": ["lunyu.x.y"],
      "spans": ["..."]
    }
  ],
  "need_clarify": false
}
```

2. 再用模板或第二次短生成把论断渲染成可读段落；**渲染不得新增无编号论断**。

Prompt 按轨约束：经轨无 `evidence_ids` 则丢弃；用轨强制前缀「现代发挥」；译轨必须保留汉字核心词。

**核验（§3.3.4，组合实现）**

| 步骤 | 第一期（规则，4 周内可跑） | 第二期（模型，12 月前） |
|------|---------------------------|-------------------------|
| 引用合法 | `ref_id` 必须在本次 bundle | 同左 |
| 论断–片段对齐 | 字面重叠 / 关键词 | NLI 或受约束 LLM |
| 支持状态 | 无证据→无依据；有重叠→支持/部分 | 独立测试集上的 F1 |
| 分轨检查 | 用轨未标、经轨无原文 → 改标或拦截 | 分类器 F1 |
| 术语 | `terms.yml`：仁/礼/义/恕 多译法 | 英回答缺汉字则警示 |

SSE 新事件（替换旧 `verify` 数字）：

```text
event: claim     {claim_id, text, track}
event: evidence  {claim_id, ref_id, span, ev_type}
event: status    {claim_id, support_status}
event: warn      {code: unsupported|conflict|term}
```

前端 `chat/page.tsx` + `lib/api.ts` 按事件改论断卡；颜色按 §3.1.2。

**拒答：** `classify=unanswerable` 或核验后关键论断全无依据 → 澄清问句或「证据不足」，禁止流畅编造。

### 3.3 可演练链 — 规则出处化状态机（应用创新）

**已有：** `liHostLogic.ts` 揖/序/席/时机 + `geomTotal`。  
**要补：** 规则对象化、出处、服务端裁定、复盘回章句。

1. 把每条规则写成 `li_rules` 一行（迎宾优先、揖深区间、席位、照应窗、过度殷勤）。  
2. `source_ref` 能填则填（如乡饮酒义、曲礼相关句）；填不上的必须写 `abstraction_note`（教学抽象，非史实测量）。  
3. 每种规则配 5 类例：正/过/不及/边界/冲突，做成 `backend/tests/test_li_rules.py`。  
4. 反馈文案带「查看依据」→ `GET /passages/{source_ref}`。  
5. 演练结束 `recap`：命中规则、相关概念（敬/序/节）、建议再问的一句话。  
6. 几何平均保留为聚合，文档与 UI 写明零值处理；**不宣传为数学创新**。

三维场景少改；改的是反馈面板和规则数据。

### 3.4 学习档案（先建议，后互馈）

`learning_events`：读过的 `ref_id`、核验警示、仪礼 `rule_id`。  
复盘只出可关闭建议（§3.3.7）。**不要做自动改检索权重**，除非 2027.02 用户实验证明增益。

## 4. 前端最小改动（10 分钟主线）

首页只留「开始切问 / 进入近思」（可先藏 feed 入口，不必删代码）。

| 页面 | 改什么 |
|------|--------|
| `/chat` | 论断卡 + 证据卡 + 离散状态；点论断进 `/read?ref=` |
| `/read` | 已有书篇句，补「从这条去演练」若概念含礼 |
| `/journey/li` | 反馈条展示规则出处；结束进复盘，不要只弹总分 |
| `/graph` | 答辩不走；关系证据在 chat 里用迷你路径条即可 |

视觉：墨=经，深蓝=注，朱砂=用，金棕=译，灰=警示。不要文化分环形图。

## 5. 评测怎么跟开发绑在一起（第 4 章）

不要等「系统完美」再造题。与开发同步：

| 阶段 | 题目规模 | 用途 |
|------|----------|------|
| 现在–9 月 | 80 题（中英），开发/测试 1:1 先混着标，**10 月底切开** | 驱动接口 |
| 10–11 月 | 扩到 300 | 第一次消融 |
| 12 月 | 600，测试集约 200+ **封存** | 赛道复核 |

目录建议：`eval/gold/v1/*.jsonl`，字段按 §4.2.2。  
脚本：`python -m app.eval.run --system B0|B1|B2|B3|B4|ours`，同一 `get_llm()`。  
现有 `eval_rag.py` 可当 B1 雏形，指标换成引用精确率/覆盖率/错引率，不要再报 10 条 Hit@1=100%。

仪礼：pytest 覆盖 §4.6.1，与 3D 脱钩，纯规则函数可测。

## 6. 工程与接口

**新/改路由（与 §3.4 对齐，可逐步加，旧 `/li/host/*` 内部转调）**

- `POST /chat`：SSE 事件换新，保留 `done.answer` 纯文本兜底给旧客户端  
- `GET /graph/evidence-path?from=&to=`  
- `GET|POST /practice/li/...`  
- `GET /learning/profile`

**降级（NFR-04 / 5.5）**

- 向量挂 → 关键词  
- 图挂 → 仅文本，关系题标「未使用图谱」  
- 模型挂 → 冻结演示题的 `claims_json` 缓存（须向评委说明）

**CI 最低集：** 规则单测 + chat 结构单测（mock LLM）+ 一条 e2e「问仁 → 有 claim 和 ref_id」。

## 7. 分阶段排期（对齐文档 6.7，可执行到周）

### 阶段 A｜2026.08–09 地基（约 4 周）

1. 冻结范围、赛道暂定 Web、权属口头对齐。  
2. 落地 `claims` / `li_rules` / `graph_edges` 来源字段。  
3. 定 SSE 与论断 JSON schema，前端先用 mock 画出论断卡。  
4. 论语数据卡 V0 + 80 题标注手册草稿。  
5. 仪礼规则表初稿：每条规则先填 `abstraction_note`，有出处的再补 `source_ref`。

**阶段门：** mock 走通「一问一验一礼」界面，不依赖真核验。

### 阶段 B｜2026.09–11 可溯源打通

1. 分型检索 + 关系题接 `graph_evidence`。  
2. 生成改为「先 JSON 论断」；引用必须是 bundle 内 id。  
3. 开发集调重排；开始 B0/B1 对比草稿。

**阶段门：** 关系题能展示带来源的路径；错引率在开发集上可统计。

### 阶段 C｜2026.10–12 可核验做实

1. 规则核验器上线，去掉对外三分数。  
2. 分轨人工抽检，迭代 prompt / 后处理。  
3. 评测集扩到 300+，第一次消融（去图 / 去分轨 / 去拦截）。  
4. 12 月按 §2.5.2 决定是否冲 AI 赛道。

**阶段门：** 无依据论断能被拦或标灰；专家抽检有记录。

### 阶段 D｜2027.01–02 可演练与试用

1. 规则出处化 + pytest 全排列。  
2. 复盘跳转阅读。  
3. 找 1 个课堂/社团走通流程（规模按文档，达不到就如实写）。

### 阶段 E｜2027.03–04 发布

公网、CI、压测、断网缓存、材料与软著名称对齐。4 月后不加工功能。

## 9. 明确不要做的实现

- 不要把 10 个智能体做成 10 次 LLM。分类用规则即可。  
- 不要为「文化分」再训一个回归头。  
- 不要先做状态互馈自动改检索。  
- 不要为了评测好看去刷种子用户。  
- 不要在分轨未稳时把五语和开放 API 当主线开发。

## 10. 第一个可开工的最小切片（建议本周）

只做这一刀，就能把 V0.3 从文档变成代码约束：

1. 定义 `Claim` JSON schema 与四种 `track`、五种 `support_status`。  
2. `orchestrator` 在 mock 模式下输出 2–3 条假论断 + 真 `ref_id`（从现有 retrieve 取）。  
3. 前端论断卡点进阅读。  
4. 礼艺反馈里给一条规则加 `abstraction_note` 展示。

这一刀不追求核验 F1，只锁数据契约。契约稳了，三条链才能分头做。
