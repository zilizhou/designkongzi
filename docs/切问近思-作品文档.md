# 第 1 章 需求分析

## 1.1 项目背景与问题分析

### 1.1.1 题目所圈定的问题

本作品名称取自《论语·子张》「博学而笃志，切问而近思，仁在其中矣」。软件需求由此收束为两个必须同时成立的目标：

- **切问**：用户用任意支持语言提问儒家概念或章句时，系统给出的每一条关键论断须能回溯到可点击的原文出处，并区分「原文依据、现代发挥、文化格义」三类信息，而不是只给出一段流畅解释。
- **近思**：用户须能在浏览器中完成至少一次可计分的「执礼」练习（迎宾次序、揖礼深浅、安席、席间照应），用敬、序、节衡量过犹不及，而不是只阅读礼的定义。

二者缺一，则题目不成立：只有问答是又一个「问孔子」；只有游戏是又一个文创六艺。

### 1.1.2 现实问题

大模型已使「问孔子」的门槛接近于零。用户输入 “What is ren?” 即可得到流畅回答。对文化传播而言，风险不在「模型不会说」，而在「说得越流畅，误读越难被发现」。本作品将失败模式分为三类，对应不同伤害：

| 失败类型 | 表现 | 对学习者的伤害 |
|----------|------|----------------|
| 无出处（幻觉） | 编造篇名、错引原文、把注疏说成孔子原话 | 误以为「有经典依据」 |
| 错时代 | 用当代人权、心理疗愈等框架直接改写经文且不加标注 | 经典被掏空，只剩现代话语的古典包装 |
| 错格义 | 将仁等同于 benevolence、礼等同于 ritual manners | 以为已经懂了，实际完成了范畴替换 |

现代发挥在国际传播中是必要的，但必须标明「这是引申」。礼同时是实践之知：讲得懂「宾主有序」，做一次迎宾仍会乱序、过恭或怠慢。因此需求陈述为：

> 在大模型已经能够流畅谈论儒家的前提下，如何让回答仍然可核对、可区分，并让人通过一次可计分的练习把礼做出来？

### 1.1.3 政策与课题背景

近三年国家持续强化中华优秀传统文化的创造性转化、创新性发展，以及国际传播能力建设。与本作品直接相关的公开部署包括：

- 2023 年文化传承发展座谈会：建设中华民族现代文明，强调融通中外、贯通古今。
- 2023 年 10 月全国宣传思想文化工作会议提出的「七个着力」：赓续中华文脉、推动两创；加强国际传播能力建设、促进文明交流互鉴。
- 2024 年党的二十届三中全会《决定》：全面提升国际传播效能，建设全球文明倡议践行机制。
- 2025 年国办发〔2025〕4 号：支持文化科技融合、文化领域大模型与数字文化国际化。
- 2026 年 1 月教育部等七部门（含中央宣传部）《关于深入推进中华优秀语言文化传承发展 提高全民语言文化素养的意见》：数字赋能、推广传播、交流互鉴。

更早但仍作总依据的，是 2017 年中办、国办《关于实施中华优秀传统文化传承发展工程的意见》（支持中华典籍走出去、国际汉学交流），以及 2021 年教育部《中华优秀传统文化进中小学课程教材指南》（《论语》等进入课程教材）。

政策用语是中华优秀传统文化、中华典籍、国际传播，而不是单独的「儒家传播条例」。儒家思想是其中明确的思想资源。本团队工作依托中宣部相关课题，需求是可演示、可核对、可练习的交互系统，而不是宣传页或到达率报表。课题是需求来源，不是技术贡献本身。

### 1.1.4 技术背景对需求的约束

检索增强生成（RAG）缓解幻觉（Lewis 等，2020），RAGAS 将 faithfulness 定义为论断能否被检索片段支持（Es 等，2024）。这只覆盖切问的第一维。知识增强与 GraphRAG 说明结构化知识应进入问答（Zhang 等，2019；Wang 等，2021；Edge 等，2024），而不是只做前端展览。跨文化评测（CulturalBench 等）证明模型有文化知识缺口，但题目不是经学格义。因此：

- 通用 RAG 不区分「原文」与「现代发挥」；
- 现成文化基准不处理「仁 ≠ benevolence」；
- 「过犹不及可计分」不属于 NLP 评测，属于把价值写成规则的交互需求。

这些缺口直接导出第 1.2、1.3 节的用户需求与功能列表。

## 1.2 用户需求分析

### 1.2.1 用户角色

| 角色 | 典型场景 | 核心诉求 |
|------|----------|----------|
| 海外学习者 | 用英语或母语问「仁是什么」「仁和礼什么关系」 | 能看原文、能分清翻译是否替换了概念 |
| 汉语国际教育教师 | 课堂演示一句问答 + 一次揖礼 | 10 分钟内走完切问与近思，过程可见 |
| 国内学生 / 青年用户 | 读一章、问一句、练一艺 | 无登录墙、手机可玩、对错说得清 |
| 课题与文化机构 | 嵌入金句或调用开放接口 | 出处稳定、配额可控，不把幻觉当成果 |

### 1.2.2 功能性需求

| 编号 | 需求 | 验收要点 |
|------|------|----------|
| FR-01 | 提问后流式返回答案 | 首字可见；中断不导致页面崩溃 |
| FR-02 | 答案绑定出处 | 每条关键论断可点击至书·篇·句（ref_id） |
| FR-03 | 三维校验可见 | 界面分别展示依据分、发挥标注、格义提示（做成后不得写死常数） |
| FR-04 | 多跳概念 | 「仁与礼」类问题须能利用概念–篇章关系，而不仅是向量近邻 |
| FR-05 | 五语可用 | 界面与经典译文至少覆盖 zh / en，并预留 fr / es / ar |
| FR-06 | 执礼可练 | 迎宾序、揖深浅、安席、照应时机可操作，输出敬 / 序 / 节与几何平均总分 |
| FR-07 | 过犹不及 | 过恭、轻慢、乱序、过度殷勤须能扣分并给出文言式评语 |
| FR-08 | 游客可用 | 首次访问自动发号，进度可保留，可升级正式账号 |
| FR-09 | 阅读溯源 | 读一读支持原文 / 译文 / 注释分层开关，并跳转「问这一句」 |
| FR-10 | 机构调用（附属） | 开放 passages / concepts 只读接口，须带出处字段 |

### 1.2.3 非功能性需求

| 编号 | 类型 | 要求 |
|------|------|------|
| NFR-01 | 可演示 | 浏览器访问，现场可走通「英文提问 → 依据卡 → 礼艺一揖」 |
| NFR-02 | 可部署 | Docker Compose 一键拉起前端、后端、图库 |
| NFR-03 | 延迟 | 常见问答 P95 首字延迟以可感知流畅为准（目标 < 1.5s，视模型网关而定） |
| NFR-04 | 合规 | 游客与注册用户可导出 / 删除个人数据；不在文档中把种子数据写成真实用户规模 |
| NFR-05 | 国产模型路线 | 生成模型采用通义等国产工具，符合大赛 AI 工具要求 |
| NFR-06 | 可离线兜底 | 检索可降级关键词；图库可降级内存图，保证断网演示不空白 |

### 1.2.4 明确不做的需求

短视频信息流、心灵鸡汤人设、自训「儒家大模型」、用访问量代替校验质量，均不作为本作品需求。它们既不切问，也不近思。

## 1.3 主要功能

功能按题目分成两条主链，其余为支撑。

### 1.3.1 切问主链

1. **经典问答**：用户输入问题，系统经路由、检索、（图谱邻域）、约束生成，SSE 流式输出；前端展示智能体状态、依据卡、校验徽章、追问。
2. **出处阅读**：书 / 篇 / 句三级导航；原文、拼音、译文、注释可开关；从依据卡跳入对应句。
3. **概念与图谱**：人物、概念、篇章、命题、学派节点；邻域钻取与两点路径；服务于「仁–礼」多跳，而不是只展览。
4. **跨语与格义提示**：非中文提问激活译文与术语对照；对易被替换的核心概念给出「不可简单等同」提示。

### 1.3.2 近思主链

1. **礼 · 执礼宾至如归**（近思核心）：3D 庭院迎宾；揖礼深度按尊卑区间计分（过恭近谄 / 失之轻慢）；迎宾次序、安席、席间时机与过度殷勤进入敬 / 序 / 节；总分几何平均。
2. **乐 / 射 / 御 / 书 / 数**：同一「不可偏废」思想下的练习（和而不同、反求诸己、礼以行之、识字明义、不患寡而患不均）。文档与答辩以礼为必演示，其余为扩展，避免写成六套互不相干的游戏合集。

### 1.3.3 支撑功能

游客鉴权与个人进度、君子之路总览（六艺分数与勋章）、开放只读 API 与嵌入金句。支撑功能在文档中的篇幅须小于两条主链。

## 1.4 竞品分析

比较维度只取切问与近思，不比较模型参数量或语料规模。

| 竞品类型 | 代表 | 已解决 | 未覆盖 | 对本作品的启示 |
|----------|------|--------|--------|----------------|
| 孔子人设聊天 | CGTN Ask Confucius；Historic Mentor 等英文导师 | 愿意开口 | 论断级出处、发挥/格义、可练的礼 | 降低门槛可学，但不能停在陪伴 |
| 古籍大模型 / 智能体 | 南农「荀子」；南大「子曰」 | 领域能力、知识库、专家标准 | 显式三维校验；礼的程序化 | 承认其语料与训练更强；本作品不拼续训 |
| 数字人文图谱 | 北大《论语》复用可视化、文献溯源；论语知识图谱；左传图谱问答 | 互文、概念网、学者阅读 | 图谱进入生成式问答；跨语学习者；体感 | 图谱必须进 chat 检索路径 |
| 六艺互动 | 场馆 VR 君子六艺；主题填字 | 科普体验 | 敬序节规则化；与问答闭环 | 浏览器可玩是特色，规则才是近思 |
| 赛事文化作品 | 古建网站、考古修复、诗词微课、剪纸文创 | 单点技术或传播形式 | 可校验问答 + 可计分的礼 | 避免做成文化门户 |

**结论：** 单点上不存在「世界首创和孔子聊天」或「世界首创知识图谱」。可守住的差异是：同一系统内同时做论断可溯源、发挥显式标注、格义可拦截，并把礼写成过犹不及的练习。相对荀子 / 子曰，本作品少模型、多约束与体感；相对 VR 六艺，本作品少头显、多规则；相对人设产品，本作品少陪伴、多核对。

# 第 2 章 概要设计

## 2.1 系统总体设计

系统为 B/S 结构：浏览器（Next.js）+ FastAPI 后端 + 关系库 / 向量库 / 图库。智能体是编排手段，不是十次串行 LLM 调用。总体分层：

```
用户终端（桌面 / 手机浏览器）
        │  HTTPS / SSE
接入与鉴权（JWT、游客发号、语言与设备）
        │
应用层 ─┬─ 切问：对话编排（路由 → 检索 → 图谱 → 合成 → 校验）
        ├─ 近思：六艺规则与成绩
        ├─ 内容：书篇句 / 译文 / 概念
        └─ 支撑：用户、开放 API、埋点
        │
数据层 ─┬─ SQLite / PostgreSQL（结构化与成绩）
        ├─ Chroma + bge-m3（跨语检索，可降级关键词）
        └─ Neo4j 或内存图（邻域 / 路径，可降级）
        │
模型层 ── 通义千问（DashScope），可切 mock 以保证演示
```

设计原则：可追溯优先（ref_id 贯穿问答与阅读）；智能体能并行则并行；经典文本预计算、强缓存；无状态服务 + 有状态存储。

## 2.2 技术路线设计

| 层次 | 选型 | 理由 |
|------|------|------|
| 前端 | Next.js 14、React、TypeScript、Tailwind | 一套代码适配多端；SSE 手写解析以支持 POST |
| 切问交互 | 依据卡 + 校验徽章 + 智能体状态条 | 让过程可被评委看见 |
| 近思交互 | React Three Fiber（礼、射等）、Web Audio（乐）、Canvas（御、书） | 浏览器内完成，不依赖头显 |
| 后端 | Python 3.11、FastAPI、SQLAlchemy 2 | 与 RAG / LLM 生态一致，原生 SSE |
| 生成 | 通义千问（国产工具路线） | 符合大赛 AI 工具要求 |
| 检索 | Chroma + bge-m3，关键词兜底 | 跨语召回；无向量库时仍可演示 |
| 图谱 | Neo4j 或内存邻接表 | 图进问答；现场可降级 |
| 部署 | Docker Compose（frontend / backend / neo4j） | 可复现安装 |

技术路线对准四条创新（2 面 + 2 点，见 6.4）：图文融合检索 → 经注分轨生成 → 仪节状态机计分 → 切问与近思状态互馈。三维校验不再是一段话上贴三个分数，而是分轨之后的核对层。**分轨、互馈、图进问答尚未做实；仪节规则已落地。未做实项不得写成已完成创新。**

## 2.3 功能模块划分

| 模块 | 对应题目 | 主要职责 |
|------|----------|----------|
| M1 对话编排 | 切问 | 路由、检索调用、生成、校验、SSE 事件 |
| M2 检索 | 切问 | 向量 / 关键词召回 Evidence |
| M3 图谱 | 切问 | 邻域、路径，向 M1 提供多跳证据 |
| M4 内容 | 切问 | 书篇句、译文、注释、概念 |
| M5 礼艺规则 | 近思 | 揖、序、席、时机、几何平均 |
| M6 其他六艺 | 近思（扩展） | 乐射御书数成绩写入总览 |
| M7 用户与进度 | 支撑 | 游客、注册、君子之路、收藏 |
| M8 开放接口 | 支撑 | 机构 Key、只读 passages / concepts |

## 2.4 模块关系与调用流程

**切问一次请求：**

```
用户提问
  → M1 路由（语言、是否议题、是否需翻译）
  → M2 检索 Top-k 句
  → M3 若问的是概念关系，取邻域 / 最短路，并入证据
  → 通义流式生成（只允许依据证据作答）
  → 三维校验（目标：论断级；现状：部分启发式）
  → SSE：agents / citation / token / verify / followups / done
  → 前端依据卡 + 徽章；用户可跳 M4 阅读该句
```

**近思一次执礼：**

```
进入礼艺场景
  → 前端规则（M5）判定迎宾序 / 揖深浅 / 安席 / 照应
  → 汇总敬、序、节，几何平均总分
  → 回传成绩，写入君子之路
  → 评语与解锁原文（接回切问的出处体系）
```

两条链通过 **出处（ref_id）** 和 **不可偏废** 对齐。进一步的互馈（近思短板改写下一轮检索，切问短板推送对应仪节）见 3.3.6，为待实现的「面」创新。

# 第 3 章 详细设计

> 本章按实现展开。V0.1 先给出结构与已落地要点；界面线框、表结构全量和三维校验伪代码在后续版本补全。

## 3.1 界面设计

主路径界面须保证 10 分钟答辩可演示：

1. 首页进入「聊一聊」或「君子之路」。
2. 对话页：输入区、流式正文、左侧或卡片区依据（书名篇名原文）、校验三维、追问 chips。
3. 阅读页：从依据卡进入对应句，五层信息可开关。
4. 图谱页：从概念跳入邻域。
5. 礼艺页：3D 庭院、宾客、席位、敬序节条与总分。

视觉沿用宣纸底、朱砂强调、墨青文字，避免满屏水墨装饰。不做与切问近思无关的运营弹窗。

## 3.2 数据库设计

核心实体（已实现）：

- `books` / `chapters` / `passages`：可寻址树，`passages.id` 为全平台溯源主键（如 `lunyu.yanyuan.12.1`）。
- `translations` / `annotations`：多语译文与注疏。
- `concepts` / `persons` / `graph_edges`：概念与图关系。
- `conversations` / `messages`：会话；`messages.citations`、`verify_scores`、`agents_used` 供回放。
- `users` 及六艺成绩、勋章、收藏。
- `institutions` / `api_keys` / `api_calls`：开放接口（附属）。

详细字段、ER 图与索引策略在后续版本附图。原则：答案不存「无出处的最终文本」作为唯一事实，必须能回到 `passage_id`。

## 3.3 关键技术设计

### 3.3.1 经典语料与可寻址出处

句为最小引用单位。生成与前端依据卡只引用 `ref_id`，禁止模型自造篇名。

### 3.3.2 图文融合的分型证据束（点）

普通 RAG 只返回相似句。本作品把一次检索做成分型证据束：向量或关键词召回候选句；概念关系类问题走图谱邻域或最短路；每条证据标注 `original` / `annotation` / `translation`；融合分 `s = α·sim + β·1/(1+dist_graph) + γ·type_prior`（原文权重大于译文）。生成只看见束。`retrieve()` 对外稳定，可切换 vector / keyword / auto。

### 3.3.3 知识图谱进入问答

图存储可插拔（内存 BFS / Neo4j）。必须进入 3.3.2 第 2 步，而不是只服务前端力导向图。现状：图服务与可视化已有，与对话编排接通为优先项。

### 3.3.4 经注分轨生成与校验（面）

输出分成两条轨道，而不是「一段解释 + 三个徽章」：

- 述轨（经）：只允许有 `ref_id` 的原义转述，无证据则禁发。
- 作轨（注 / 现代发挥）：允许当代转译，必须整段标记为引申。
- 格义层：跨语时仁、礼、恕、义等保留汉字，对照译名旁标注不可简单等同。

校验在分轨之后：述轨做论断–证据对齐，作轨查漏标，格义层查术语锁。现状为单轨生成加启发式分数，分轨待做实。

### 3.3.5 仪节状态机与评分代数（点）

礼写成可验证过程：状态含未迎宾集合、当前揖对象、席位映射、时间轴事件；转移须满足尊卑优先、揖深区间、位次一致、照应时间窗；非法转移给出过恭近谄 / 失之轻慢 / 失序 / 失于节。聚合 `geomTotal = (jing × xu × jie)^(1/3)`。规则已在礼艺落地，待补形式化定义与回归用例。

### 3.3.6 切问–近思状态互馈（面）

用户状态同时记录切问短板（依据弱 / 发挥未标 / 格义触发）与近思短板（敬 / 序 / 节）。例如：序分低则检索加权宾主有序类篇章；格义触发「仁 = benevolence」则推一趟须区分敬与谄的揖礼；述轨依据不足则先打开对应句再继续问。无互馈则仍是拼盘。本项待实现。

### 3.3.7 接口设计

切问：`POST /api/v1/chat`（SSE：agents / token / citation / verify / followups / done）。  
阅读：`GET /api/v1/books|chapters|passages`。  
图谱：`GET /api/v1/graph/concept/{id}/neighborhood`，`GET /api/v1/graph/path`。  
礼艺：`GET /api/v1/li/host/today`，`POST /api/v1/li/host/{key}/result`。  
开放：`GET /api/v1/public/passages|concepts`（API Key）。

# 第 4 章 测试报告

> V0.1 先规定测什么。评测集与公网压测按计划后置，不在本章虚构指标。

## 4.1 测试目标

验证切问主链可走通、出处可点、礼艺规则与「过犹不及」一致；标明三维校验哪些已测、哪些未做实。

## 4.2 测试环境

本地：macOS / Linux，Docker Compose，浏览器 Chrome。模型：通义或 mock。数据：内置经典种子，不以种子用户规模作为测试结论。

## 4.3 场景测试（建议用例）

| 编号 | 场景 | 期望 |
|------|------|------|
| S1 | 中文问「何谓仁」 | 出现《论语》依据卡，可跳转阅读 |
| S2 | 英文问 What is ren? | 英文作答，仁字保留，不得只剩 benevolence |
| S3 | 问「仁与礼的关系」 | 应动用概念关系，而非两段无关引文 |
| S4 | 礼艺故意后迎尊者 | 序分下降，评语指出失序 |
| S5 | 礼艺揖过深 | 敬分下降，评语过恭近谄 |
| S6 | 只刷一维、其余极低 | 几何平均明显低于算术平均 |

## 4.4–4.6 一致性、人工复核与结果分析

待三维校验做实后：抽取不少于约定条数的问答，人工标「依据 / 发挥 / 格义」是否判断正确，报告一致率。礼艺用固定操作序列回归，防止改场景后规则漂移。

## 4.7 现有问题与改进方向

1. 校验两项仍为占位，须改为论断级。  
2. 图谱尚未稳定进入对话检索。  
3. 六艺叙事需统一到敬序节 / 不可偏废，避免游戏合集观感。  
4. 生产环境曾为内网地址，参赛须准备可访问部署（后置任务）。

# 第 5 章 安装与使用

## 5.1 系统运行环境

- 操作系统：Linux 或 macOS（Windows 经 Docker）  
- 容器：Docker、Docker Compose  
- 浏览器：Chrome / Edge 近两年版本  
- 可选：DashScope 密钥（不通则 mock）

## 5.2 系统安装说明

克隆仓库后，按仓库 `DEPLOY.md` 与 `docker-compose.yml` 启动 `frontend`、`backend`、`neo4j`。环境变量放入 `.env`，勿提交密钥。首次需导入经典种子与向量（若启用）。

## 5.3 系统使用流程

游客打开首页 → 聊一聊提问 → 点依据卡阅读 → 君子之路进入礼艺完成一揖 → 查看敬序节。

## 5.4 典型使用示例

答辩演示脚本：英文问仁 → 指出依据卡与三维（或占位说明）→ 图谱看仁的邻域 → 礼艺迎一位宾客并解释几何平均。控制在 10 分钟内。

## 5.5 注意事项

勿将种子数据、内网 IP、未做实的校验分数写入对外宣传为「已达指标」。现场准备 mock 与热点双备份。

# 第 6 章 项目总结

## 6.1 项目分工

（填写：需求与文档 / 切问编排与检索 / 图谱 / 礼艺与六艺 / 前端交互 / 测试。作者须为同校在籍本科生 2–9 人。）

## 6.2 风险分析与对策

| 风险 | 对策 |
|------|------|
| 被问「不就是套了通义」 | 答辩只讲约束、出处、礼的规则，不讲模型更大 |
| 校验未做实被揭穿 | 文档诚实分期；演示以礼艺规则 + 出处卡为已完成硬点 |
| 知识产权与课题成果 | 软著权属先问科研处；学校为著作权人时须书面授权参赛 |
| 现场断网 / 接口额度 | mock、关键词检索、内存图降级 |
| 功能过多讲成门户 | 10 分钟只走切问近思一条线 |

## 6.3 推广与应用设想

汉教课堂演示、海外学习者自习、课题开放接口。不把未发生的用户规模写入推广成效。

## 6.4 创新点与特色总结

四条创新，**两面两点**。面管「整件作品为什么不是拼盘」，点管「评委能追问公式的那一层」。旧表述里的「三维徽章」和「六艺可玩」分别升格为分轨架构与仪节状态机，并补上检索融合与状态互馈两条技术。

| 编号 | 点/面 | 名称 | 和直接问通义的差别 | 实现状态 |
|------|-------|------|--------------------|----------|
| I1 | 面 | 经注分轨的可核对生成 | 先分成「述（有据原义）」与「作（标明发挥）」再生成；格义在跨语层锁术语。不是一段话贴三个分数。 | 待做实 |
| I2 | 面 | 切问–近思状态互馈 | 问答短板改写下一轮检索与练习，练习短板改写下一轮提问。不是聊天旁边挂游戏。 | 待做实 |
| I3 | 点 | 图文融合的分型证据束 | 向量相似 + 图谱多跳 + 原文/注疏/译文分型后融合排序。图谱进生成，不只进展览。 | 检索与图库已有，融合未接通 |
| I4 | 点 | 仪节状态机与过犹不及评分代数 | 迎宾/揖/席/时机是可验证状态转移；总分几何平均，一维低则整体低。 | 礼艺规则已落地，待补形式化与回归 |

**特色（不叫创新）：** 浏览器内六艺可玩、依据卡与过程可见、五语骨架、图谱可视化、开放只读 API。

**不是创新：** RAG 一词本身、通义模型、Neo4j 展览、智能体名称、中宣部课题身份、种子用户数字。

答辩只展开 I1–I4。I4 是目前唯一能现场硬证的点；I1–I3 按实现进度诚实分期，做实一条讲一条。

## 6.5 现阶段成果与可交付性

已可运行：对话与依据卡、阅读、图谱页、礼艺 3D 及仪节规则、部分其他六艺、Docker 部署。待做实：经注分轨、图文融合接通对话、状态互馈、公网演示、评测集。软著在锁名后登记，名称与本文作品名称一致。
